# Jarod-OS : analyse de l'application, redimensionnement des fenêtres, récupération depuis DSH NEXT

Date : 2026-10-12. État analysé : branche `feature/windows-port`, commit `12be499` (rien de poussé). Analyse en lecture seule : aucun code de l'application n'a été modifié.
Les constats marqués **[vérifié]** ont été reproduits sur une instance jetable (profil temporaire, ports dédiés, arrêtée ensuite) ; **[lu]** = lu dans le code ; **[estimé]** = à confirmer.

## 1. Redimensionnement des fenêtres

Deux niveaux : la fenêtre Electron (le « bureau ») et les fenêtres internes du shell (`src/store/windows.ts`, `src/shell/wm/Window.tsx`).

### Ce qui fonctionne [vérifié]
- Fenêtre Electron : redimensionnée de l'extérieur par l'API Win32 à 1100×700, 1700×950, 1366×768 : la page suit (viewport = fenêtre − 12 px de bordure invisible), la fenêtre principale se recolle à la zone utile, aucune erreur. Le minimum 1024×640 est respecté (demande 800×500 → 1036×646 mesurés).
- Vue web native (fenêtre « Web » / Studio) : alignée sur son cadre après un redimensionnement interne (arête est tirée de −300 px) **et** après un redimensionnement de la fenêtre Electron (captures d'écran : le liseré jaune de la page témoin épouse le cadre).
- Maximiser / restaurer / fermer / réduire de la fenêtre Electron : déjà couverts par `window-controls.test.ts`.

### Défauts constatés (dans l'ordre de gêne)
| # | Défaut | Preuve | Cause |
|---|---|---|---|
| W1 | Tirer l'arête **ouest ou nord** au-delà de la taille minimale **fait glisser la fenêtre** au lieu de s'arrêter (arête droite 1000 → 1259, arête basse 600 → 809). | [vérifié] en vrai (souris CDP) | `setBounds` borne la largeur à 360 mais pas `x` ; le déplacement `x = départ + dx` continue. |
| W2 | Tirer l'arête **est** au-delà de l'écran **déplace le bord gauche** (300 → 287, ou → 14 si on dépasse beaucoup) au lieu de stopper le bord droit. | [vérifié] en vrai + test unitaire | `clamp` réduit la largeur puis recale `x`. |
| W3 | Quand l'écran rétrécit puis revient (dock auto-hide, RDP, double écran débranché), **les fenêtres gardent la petite taille** : 1200×700 → 996×582 à 1024×640, et reste 996×582 après retour à 1700×950. | [vérifié] en vrai | `relayoutOnResize` écrase `bounds` par la version bornée, sans mémoriser la taille voulue. |
| W4 | Les **poignées de coin** (12 px, `rounded-2xl` = 16 px) sont presque inatteignables : à 5 px du coin, la cible touchée est le cadre, pas la poignée. Les arêtes ne font que 6 px. | [vérifié] `elementFromPoint` | Poignées à l'intérieur d'un cadre `overflow-hidden` arrondi. |
| W5 | Le minimum 360×240 est **global** : la Caméra (260×290 par défaut) passe à 360 de large dès le premier redimensionnement. | [vérifié] test unitaire | `setBounds` ne lit pas de minimum par application. |
| W6 | Pas de mémoire de la taille/position de la **fenêtre Electron** entre deux lancements (toujours la zone utile de l'écran principal, plein écran par défaut) ; pas de manipulation au clavier ni d'aimantation (moitié d'écran, Win+flèches). | [lu] | `createMainWindow` n'utilise que `getPrimaryDisplay().workAreaSize`. |

### Correctif proposé (petit, testable)
1. Dans `Window.tsx`, calculer le redimensionnement **à partir de l'arête opposée fixe** : pour `w`/`n`, `x = droite − largeur_bornée` (borne [min, droite − area.x]) ; pour `e`/`s`, `largeur = min(demandée, area.droite − x)`. `setBounds` ne recale plus `x` pour un redimensionnement (seulement pour un déplacement).
2. Garder `preferredBounds` (taille voulue) à côté de `bounds` (taille affichée) : `relayoutOnResize` recalcule l'affichage depuis `preferredBounds`.
3. `minSize` par application dans `apps.ts` (Caméra 220×240, Widget 240×160, le reste 360×240).
4. Poignées : arêtes de 8–10 px débordant de 4 px à l'extérieur, coins de 16 px posés sur un conteneur non rogné.
5. Tests : `windows.test.ts` (aujourd'hui aucun test sur ce module, alors qu'il porte tout le gestionnaire de fenêtres) avec les cas W1–W3 et W5 ci-dessus, vérifiés par mutation.

## 2. Analyse de l'application

Taille : shell ≈ 68 000 lignes TS/TSX (99 fichiers de test), noyau ≈ 58 700 lignes. Electron 44.5, React 19.3. Typecheck et tests au vert (lot 5). Points sains [lu] : `sandbox: true`, `contextIsolation`, `nodeIntegration: false`, CSP stricte (`script-src 'self'`), `will-navigate` verrouillé, permissions des vues web refusées par défaut, jeton de la passerelle écrit en 0600 + `icacls`.

### Constats à traiter
| # | Constat | Gravité | Détail |
|---|---|---|---|
| A1 | **Le second lancement ne s'arrête pas à temps** | Moyenne [vérifié] | `requestSingleInstanceLock()` est appelé en ligne 181 de `main.ts` ; avant (migration de données, `PluginHost`, `SwitchService`) et après (`whenReady`) tout s'exécute quand même. Mesuré : le second processus a écrit « Jarod-OS … starting » et **ouvert son propre serveur de contrôle** avant de quitter. Sous Linux/macOS, ce serveur supprime le socket du premier (`unlinkSync`). Correctif : réclamer le verrou en tout premier, et ne rien enregistrer si le verrou est refusé (c'est ce que fait DSH NEXT : `claimDesktopSingleInstance` renvoie `false`). |
| A2 | **Installateur trop lourd : `app.asar` = 124 Mo** | Moyenne [vérifié] | `@tabler` seul pèse 120 Mo dans l'asar ; `react-dom`, `shiki`, `@radix-ui`, `@xterm` y sont aussi alors que Vite les a déjà inclus dans `dist/`. Cause : les bibliothèques du rendu sont dans `dependencies` (pas `devDependencies`). Déplacer tout sauf `node-pty` (et ce que `main` charge à l'exécution) : l'asar tomberait à ≈ 15–20 Mo [estimé], l'installeur de 153 Mo à ≈ 100 Mo [estimé]. À reconstruire pour le confirmer. |
| A3 | Aucune gestion des plantages **du rendu / du GPU / du cœur** | Moyenne [lu] | Aucun `render-process-gone`, `child-process-gone` ni `unresponsive` dans `electron/`. Un rendu qui plante laisse une fenêtre blanche. À faire : journaliser, recharger une fois, proposer le mode sans échec (voir D3). |
| A4 | Pas de mise à jour du shell | Moyenne [lu] | Rien ne vérifie ni n'installe une nouvelle version (le catalogue Logiciels installe d'autres programmes). L'installeur NSIS est déjà produit : il manque un flux de vérification/téléchargement (voir D2). |
| A5 | Vocabulaire macOS restant | Faible [lu] | « Everything on this Mac », « Monitor and control your Mac » (`apps.ts`), « Macintosh HD » (Fichiers, Stockage), `System Settings` dans quelques messages, arithmétique de chemins POSIX de la page Fichiers (déjà signalée). |
| A6 | Pas d'icône de zone de notification | Faible | Un agent qui travaille en arrière-plan n'a pas de présence quand la fenêtre est réduite (DSH NEXT embarque ses icônes de plateau). |
| A7 | `node.exe` embarqué = 93 Mo | À évaluer | DSH NEXT lance son moteur avec l'exécutable Electron en mode Node (`ELECTRON_RUN_AS_NODE`) : −93 Mo. À vérifier : le lanceur du cœur utilise `node --permission` ; il faut confirmer que le Node d'Electron 44 le prend en charge. |
| A8 | Taille de fenêtre : voir §1 (W1–W6). | | |

## 3. DSH NEXT : ce qu'on peut en récupérer

**Ce que c'est** [lu] : `C:\Program Files\DSH NEXT`, « dsh-desktop-next 2.0.17-next » (DeepSeek Harness, Electron + paquets `@deepseek-ai/dsh-*` 0.2.0-rc.2), profils dans `C:\Users\San\.dsh`. C'est l'amont `anywhere-labs/dsh-desktop` que `upstream.json` surveille déjà avec `"portage": "autorisé"`. Les paquets sont sous **licence MIT** (champ `license` de chaque `package.json`) : réutilisables avec la mention de licence (à ajouter dans `licenses/` comme pour les autres amonts). Le code est fourni lisible (non obscurci) dans `node_modules`.

Ce que Jarod a **déjà** : compaction, mode plan, objectifs, points de reprise, sous-agents, reconnaissance vocale locale, MCP/ACP, planificateur, coffre, skills, outil `edit_file`.
