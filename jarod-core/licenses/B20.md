## B. Comment la liste a été établie (métadonnées seules)

Script `scripts/pypi_closure.py` : lit l'API JSON de PyPI (`/pypi/<paquet>/json` et `/<version>/json`), évalue les marqueurs d'environnement pour l'interpréteur cible (cp312 / win_amd64), retient la dernière version compatible de chaque paquet qui a une roue pour cette cible, jusqu'au point fixe. **Aucun paquet ni aucune roue n'a été téléchargé** (`pip install --dry-run` en télécharge : non utilisé). Les sha256, tailles et noms de fichiers viennent de cet API ; trois d'entre eux (`docling-slim`, `docling-parse`, `lxml`) ont été recoupés par un `curl` direct sur l'API, avec le même résultat. Les 54 ont une roue (aucune source à compiler).
Fichier joint : `licenses/B20-requirements.txt` (`nom==version --hash=sha256:…`).

## C. Ce que ce profil sait faire — et ne sait pas faire

Établi par LECTURE (sans enregistrer) de fichiers du dépôt `docling-project/docling`, étiquette `v2.131.0` (`docling/pipeline/native_pdf_pipeline.py`, `docling/models/stages/layout/layout_object_detection_model.py`, `docling/models/inference_engines/object_detection/onnxruntime_engine.py`) et des métadonnées des paquets :

- **PDF à couche texte** : le pipeline `NativePdfPipeline` existe et se décrit lui-même « model-free » : chaque cellule de texte du PDF devient un élément avec sa page et sa boîte, les images incorporées deviennent des éléments image ; **aucun modèle de mise en page, d'OCR ni de tableaux ne tourne, donc le document n'a « no reading order, headings or tables »** (citation du code, < 15 mots). Attendu pour ce profil : texte et **pages** oui ; **titres/sections et tableaux du PDF non**. C'est la limite principale, et elle est probablement visible à la gate de fidélité (sections, tableaux) sur les PDF.
- **DOCX, PPTX, XLSX, HTML** : leurs analyseurs (`msword_backend.py`, `mspowerpoint_backend.py`, `msexcel_backend.py`, `html_backend.py`) s'appuient sur `python-docx`, `python-pptx`, `openpyxl`, `beautifulsoup4`, en Python pur, et rendent une structure (titres, tableaux). **Que ces analyseurs n'aient besoin d'aucun modèle n'est PAS vérifié** (je n'ai pas lu leur code) : c'est ce que le test de fumée de la section E établit.
- **Non établi par les métadonnées** : qu'`import docling…` réussisse sans PyTorch. Si un import échoue faute de `torch`, c'est un **ARRÊT et un retour à l'utilisateur** — je n'ajoute rien de mon propre chef ; passer à un profil plus lourd est une nouvelle demande B.

## G. Risques connus (consignés AVANT l'exécution, pas des raisons de renoncer)

1. **Le profil peut ne pas s'importer sans PyTorch** (imports au chargement de `docling.datamodel…`, non vérifiable par métadonnées) : arrêt et retour, voir C.
2. **PDF sans titres ni tableaux** (C) : la gate de fidélité peut échouer sur les PDF pour cette raison, et c'est LE résultat attendu de l'étape Q-I2. Les suites possibles, à décider alors (aucune n'est demandée ici) : accepter « texte + pages » pour le PDF ; un profil intermédiaire (mise en page par ONNX Runtime sans PyTorch : l'analyseur `onnxruntime_engine.py` s'appuie sur le prétraitement d'images de `transformers` et sur des poids Hugging Face — **non analysé, non établi**) ; le profil `standard` (PyTorch).
3. **Versions « les plus récentes compatibles »**, pas celles d'un lot testé par les auteurs de Docling : `docling-slim==2.131.0` est fixé, ses dépendances sont les dernières satisfaisant ses bornes (`docling-core 2.99.0`, `pandas 3.0.6`, `numpy 2.5.3`…). Un échec d'incompatibilité = arrêt et compte rendu.
4. **Le worker tourne avec les droits de l'utilisateur** : hors ligne, environnement en liste blanche, threads et priorité bornés sont des consignes et des contrôles de l'adaptateur (`WorkerParser`, lot B ④), **pas une isolation forte**.
5. Le poids installé est estimé, pas mesuré.
